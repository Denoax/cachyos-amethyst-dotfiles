# Doer execution plan

## Phase 0 — establish source truth

Read root instructions and current local reports. Use `extract-desktop` skill. Determine active config files, startup owners, binding sources, theme tokens, wallpaper provider, official VS Code profile and installed integration components. Record changes in progress by another Codex session. Collect a minimal private source inventory, public-safe dependency manifest and feature status matrix. Do not treat older prompt files as completion evidence.

Checkpoint: current effective state, unresolved requested work and proposed file ownership. Continue with portable staging independent of any ambiguous interactive item.

## Phase 1 — create the new source tree

Create a local repo for `cachyos-amethyst-dotfiles`; do not clone private home state or reuse Kona history. Add this handoff's project instructions/skills. Export allowlisted config into chezmoi source, curated package manifests, theme tokens, user scripts/units and sanitized VS Code workspace/profile. Use minimal upstream overrides. Keep exact machine overrides local and ship sanitized examples.

Finish required missing accent/shortcut/daily integration items only with narrow, reversible changes and current evidence. Preserve valid user preferences and running work. Retire dead launcher commands from the advertised default; document unavailable historical shortcuts instead of remapping them arbitrarily.

Checkpoint: source commit, provenance ledger, public/private boundary and first compatibility tuple. Review staged diffs before remote use.

## Phase 2 — implement installation and recovery

Use `portable-install` skill and `installer/SPEC.md`. Implement actual commands before writing install snippets that invoke them. Make all selected components available through a short documented flow from a fresh working CachyOS Hyprland session. Scope package prompts and downloads transparently. Write meaningful temporary-home failure/idempotence/rollback tests; run them. Add CI lint/schema/link/license/secret checks.

Checkpoint: successful tests, failure cases, install/rollback CLI and supported base definition. No fresh-install claim yet.

## Phase 3 — validate clean environment and daily use

Use a disposable CachyOS VM or available test laptop, never the production disk. Verify ISO/source integrity by current official guidance before installation. Record VM graphics/session limitations. Install from the candidate repo commit using the published instructions exactly. Repeat apply, verify first login, core daily Linux matrix and VS Code flows. Exercise recovery and update behavior. Do not silently add manual fixes absent from installer/docs; fix the product, reset the test and rerun affected path.

If no VM capability or test device exists, still complete filesystem tests, source-session flows, docs and captures; mark clean-install/laptop claims blocked, and keep release status prerelease. Do not declare installability proven. Physical suspend, docking, Wi-Fi/Bluetooth and NVIDIA/Intel/AMD compatibility need appropriately scoped hardware evidence.

Checkpoint: evidence matrix, package tuple and remaining limitations. Use failed cases to narrow support claims, not delete them from the report.

## Phase 4 — record and produce public media

Use `record-showcase` skill. Discover/reuse or implement the requested showcase workflow and actually run it locally. Capture the scenes in `showcase/STORYBOARD.md`, including VS Code and Discover. Build GIF/video/poster derivatives, manifest and gallery; perform continuous review and privacy/asset review. Fix visible bugs before filming the success claim. Restore presentation-only changes afterward.

Checkpoint: every published asset maps to reviewed source footage and a tested feature. Keep masters and private logs outside Git.

## Phase 5 — publish and return

Use `publish-desktop` skill and `docs/RELEASE.md`. Complete the README/docs/credits and recheck actual GitHub rendering after push. Publish the new public repo and appropriate stable/prerelease tag when the corresponding gates pass. Return exact URLs/commit, short fresh-install procedure, rollback command, gallery and truthful verification summary. Preserve a local return report/checkpoint for the Thinker.

No circular approval loop: the user requested publication. Ask only for genuinely missing account authority, unavailable credentials or an unresolved material preference. If automatic approval review rejects an action, report the exact rejected action and reason, then complete the remaining authorized work.
